# Connecting PulseChat to MongoDB Atlas

Start to finish, about ten minutes. Free tier, no card required.

At the end you will have a `MONGO_URI` in `server/.env`, demo data in the cloud,
and `npm run start:dev` connecting to it.

> In a hurry? `npm run start:local` runs the entire backend against a throwaway
> in-memory MongoDB with no setup at all. Come back to this when you are ready to
> deploy.

---

## 1. Create an account and a project

1. Go to <https://www.mongodb.com/cloud/atlas/register> and sign up.
2. Atlas drops you into a default project. That is enough — or use
   **Projects → New Project** and call it `PulseChat`.

## 2. Create the cluster

1. Click **Build a Cluster** (or **+ Create**).
2. Choose the **M0** tier — the free one.
3. Pick a region **near you or near where you will deploy**. This is the biggest
   single factor in query latency and you cannot change it later without
   recreating the cluster.
4. Name it `pulsechat` and hit **Create Deployment**.

## 3. Create a database user

**Security → Database Access → Add New Database User**.

| Field | Value |
| --- | --- |
| Authentication Method | Password |
| Username | `pulsechat` |
| Password | **Autogenerate Secure Password**, then **Copy** |
| Privileges | **Read and write to any database** |

**Copy the password now.** Atlas will not show it again.

> Typing your own? Avoid `@ : / ? # [ ] %` — they are all meaningful inside a
> connection string. See [URL-encoding](#url-encoding-special-characters).

## 4. Allow your IP address

**Security → Network Access → Add IP Address**.

- Local development: **Add Current IP Address**.
- Deploying to Render or Railway: those hosts do not publish fixed egress IPs on
  standard plans, so you need **Allow Access from Anywhere** (`0.0.0.0/0`).
  Normal for this kind of project — your database user password is the real
  guard. Use a strong autogenerated one and never commit it.

> **The number one cause of "it won't connect."** Home IPs change; come back and
> re-add yours when they do.

## 5. Copy the connection string

**Database → Connect → Drivers → Node.js**. You get something like:

```
mongodb+srv://pulsechat:<db_password>@pulsechat.ab1cd.mongodb.net/?retryWrites=true&w=majority
```

## 6. Fix up the string

Two edits before it works:

**a. Replace `<db_password>`** — angle brackets included — with the real password.

**b. Add the database name** between the `/` and the `?`. Without it, Mongoose
connects to a database literally called `test`:

```
                                                    ┌── add this
                                                    ▼
mongodb+srv://pulsechat:s3cr3t@pulsechat.ab1cd.mongodb.net/pulsechat?retryWrites=true&w=majority
```

## 7. Put it in `server/.env`

```bash
cd server && cp .env.example .env
```

```ini
MONGO_URI=mongodb+srv://pulsechat:s3cr3t@pulsechat.ab1cd.mongodb.net/pulsechat?retryWrites=true&w=majority
JWT_SECRET=paste_the_output_of_the_command_below
```

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

`.env` is gitignored. Keep it that way.

## 8. Seed and run

```bash
npm run seed
```

```bash
npm run start:dev
```

Look for `✔ MongoDB connected — pulsechat`. If it says `— test`, you skipped 6b.

## 9. Prove it

```bash
curl http://localhost:5000/api/health
```

```json
{ "ok": true, "uptime": 3, "db": "connected", "env": "development" }
```

Then start the client and sign in as `demo@pulsechat.app` / `pulsechat123`.

## Troubleshooting

### `MongooseServerSelectionError` / `ETIMEDOUT` / hangs

Your IP is not allowlisted, ~95% of the time. Step 4 again. Corporate networks
and some public wifi also block outbound 27017; a phone hotspot confirms it.

### `Authentication failed` / `bad auth`

- The password still has `<` `>` around it, or you used your *Atlas account*
  password rather than the *database user* password from step 3.
- It contains a character needing encoding — see below.
- Fastest fix: **Database Access → Edit → Edit Password → Autogenerate**.

### `querySrv ENOTFOUND _mongodb._tcp....`

Wrong hostname, or your DNS cannot resolve SRV records. Re-copy from step 5.

### It connects but the app is empty

You started the server before seeding. Stop, `npm run seed`, start again.

### URL-encoding special characters

| Character | Replace with | | Character | Replace with |
| --- | --- | --- | --- | --- |
| `@` | `%40` | | `#` | `%23` |
| `:` | `%3A` | | `[` | `%5B` |
| `/` | `%2F` | | `]` | `%5D` |
| `?` | `%3F` | | `%` | `%25` |

An un-encoded `@` is the classic one: the driver treats everything before the
*last* `@` as credentials, so the string quietly points at the wrong host.

Or let Node do it:

```bash
node -e "console.log(encodeURIComponent('your:pass@word'))"
```

## Free tier notes

512 MB storage, shared CPU. Chat messages are tiny; this project will not come
close. M0 clusters are never deleted for inactivity, though Atlas pauses one
after 60 days of no connections — opening the dashboard resumes it.

The indexes (`{ room: 1, createdAt: -1 }` for history, `{ members: 1, updatedAt: -1 }`
for the sidebar) are created by Mongoose on first connect. Nothing to add by hand.

## Going to production

See **[deploy.md](deploy.md)**. Consider a separate database name for
production — `.../pulsechat_dev` locally and `.../pulsechat` live — so seeding
locally can never wipe real data.
