# Deploying PulseChat

Frontend on **Vercel**, backend on **Render**, database on **MongoDB Atlas**.
All three have free tiers. Budget about 30 minutes the first time.

**Do the backend first.** The frontend needs the API's URL at build time, so
deploying it first means rebuilding it afterwards.

```
GitHub repo ──┬──► Vercel   (client/)  →  https://pulsechat.vercel.app
              └──► Render   (server/)  →  https://pulsechat-api.onrender.com
                                              │
                                              └──► MongoDB Atlas
```

---

## Part 0 — Push to GitHub

### Why there are two `.gitignore` files

Git reads **every** `.gitignore` relative to the folder it sits in. So:

| File | Covers |
| --- | --- |
| `.gitignore` (root) | the whole repo — OS junk, editor files, a safety net for `.env` |
| `client/.gitignore` | `client/**` — `node_modules`, `dist`, `.env` |
| `server/.gitignore` | `server/**` — `node_modules`, `.env` |

This is the normal layout for a repo with two packages. There is nothing to
merge. Each one is scoped to its own directory automatically.

**What must never be committed:** `server/.env` holds your Atlas password and
your Gemini key. `client/.env` holds your Firebase config. Both are ignored.
The `.env.example` files *are* committed — they are placeholders only, and they
are what tells anyone cloning the repo which variables to set.

### Create the repo

```bash
cd E:\Project\PulseChat
git init -b main
git add .
```

Now **verify no secret is staged** before the first commit:

```bash
git status --porcelain | findstr /I ".env"
```

You want to see only `.env.example` lines. If `server/.env` or `client/.env`
appear, stop and fix the ignore rules before continuing.

```bash
git commit -m "feat: PulseChat - real-time chat with streaming AI assistant"
```

Create an empty repo on GitHub (no README, no .gitignore — you already have
both), then:

```bash
git remote add origin https://github.com/<you>/pulsechat.git
git push -u origin main
```

## Part 1 — Backend on Render

### 1.1 Open Atlas to Render

Render's free tier has no fixed egress IP, so Atlas has to accept any address.

**Atlas → Network Access → Add IP Address → Allow Access from Anywhere**
(`0.0.0.0/0`).

Your database user password is what actually protects the data. Make sure it is
the autogenerated one, not something you typed.

### 1.2 Create the service

<https://dashboard.render.com> → **New → Web Service** → connect your GitHub repo.

| Setting | Value |
| --- | --- |
| Name | `pulsechat-api` |
| Language | Node |
| Branch | `main` |
| **Root Directory** | `server` |
| Build Command | `npm ci --omit=dev` |
| Start Command | `npm start` |
| Instance Type | Free |
| Health Check Path | `/api/health` |

`--omit=dev` matters: `mongodb-memory-server` is a devDependency that downloads a
~100MB MongoDB binary, and production never touches it — it is only used by
`start:local` and `smoke`. `npm ci` (rather than `npm install`) installs exactly
what `package-lock.json` pins, so the deployed build matches your local one.

**Root Directory `server` is the one people miss.** Without it Render runs the
build at the repo root, finds no `package.json`, and fails.

### 1.3 Environment variables

**Environment → Add Environment Variable**, one per row:

| Key | Value |
| --- | --- |
| `NODE_ENV` | `production` |
| `MONGO_URI` | your full Atlas string, database name included |
| `JWT_SECRET` | **a new one**, not your development secret |
| `CLIENT_URL` | your Vercel origin — see Part 3. **Required in production:** the server refuses to boot if this is unset or localhost, because it would block every browser request at the CORS preflight |
| `AI_PROVIDER` | `gemini` |
| `GEMINI_API_KEY` | your key |
| `GEMINI_MODEL` | `gemini-flash-latest` |
| `AI_REQUESTS_PER_HOUR` | `30` |
| `BOT_NAME` | `Pulse AI` |

Generate a fresh secret:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

**Do not set `PORT`.** Render assigns it and injects it; the server already
reads `process.env.PORT`.

A different `JWT_SECRET` in production means tokens minted in development are
worthless against the live API, which is what you want.

### 1.4 Deploy and check

Click **Create Web Service**. First build takes 2-5 minutes. Watch the log for:

```
✔ MongoDB connected — pulsechat
  REST      http://localhost:10000/api
  Assistant Pulse AI · gemini
```

Then, from your machine:

```bash
curl https://pulsechat-api.onrender.com/api/health
```

```json
{ "ok": true, "uptime": 12, "db": "connected", "env": "production" }
```

`"db": "connected"` is the bit that matters. If it says `disconnected`, Atlas is
rejecting Render — go back to 1.1.

Copy your service URL. You need it next.

## Part 2 — Frontend on Vercel

<https://vercel.com/new> → import the same GitHub repo.

| Setting | Value |
| --- | --- |
| Framework Preset | Vite |
| **Root Directory** | `client` |
| Build Command | `npm run build` (default) |
| Output Directory | `dist` (default) |

### 2.1 Environment variables

Add these **before** the first deploy — Vite bakes them into the bundle at build
time, so adding them later means redeploying.

| Key | Value |
| --- | --- |
| `VITE_API_URL` | `https://pulsechat-api.onrender.com/api` |
| `VITE_SOCKET_URL` | `https://pulsechat-api.onrender.com` |
| `VITE_DEMO_MODE` | `false` (or omit — demo mode is opt-in) |

Note the difference: `VITE_API_URL` ends in `/api`, `VITE_SOCKET_URL` does not.
Use `https://` for the socket URL too — Socket.io upgrades to `wss://` itself.

Get either wrong and **the build fails with the exact correction**, rather than
deploying a bundle that points at localhost. `vite.config.js` checks both before
Vite emits anything.

Firebase image uploads are optional. Without those keys the upload UI falls back
to a local preview and nothing breaks. To enable them, add `VITE_FIREBASE_API_KEY`,
`VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`,
`VITE_FIREBASE_STORAGE_BUCKET`, `VITE_FIREBASE_APP_ID`.

### 2.2 Deploy

Hit **Deploy**. Copy the URL you get, e.g. `https://pulsechat.vercel.app`.

`client/vercel.json` rewrites every path to `index.html` so React Router can
handle deep links. Without it, refreshing on `/chat/<id>` returns a Vercel 404,
because that file genuinely does not exist on disk.

Keep that file free of comments. JSON has none, and the `"//": "..."` trick that
works in some tools is rejected here — Vercel validates `vercel.json` against a
strict schema and fails the deploy on any unrecognised property.

## Part 3 — Close the loop

The API is still allowing `placeholder.vercel.app`, so the browser will be
blocked by CORS until you fix it.

**Render → pulsechat-api → Environment → `CLIENT_URL`** → set it to your real
Vercel URL:

```
CLIENT_URL=https://pulsechat.vercel.app
```

**No trailing slash.** The check is an exact string match in production, and
`https://pulsechat.vercel.app/` will not match `https://pulsechat.vercel.app`.

Want Vercel preview deployments to work too? `CLIENT_URL` accepts a
comma-separated list:

```
CLIENT_URL=https://pulsechat.vercel.app,https://pulsechat-git-main-you.vercel.app
```

Render redeploys automatically when you save. Wait for it, then open your Vercel
URL and sign in with `demo@pulsechat.app` / `pulsechat123`.

## Verifying the deploy

Work through these in the browser, with DevTools open:

1. **Sign in** — no CORS error in the console.
2. **Open a room** — history loads.
3. **Sidebar footer says CONNECTED** — the socket is live, not just REST.
4. **Two browsers, same room** — send from one, it appears in the other without
   a refresh. This is the whole product in one test.
5. **Type `@ai hello`** — the reply fills in progressively rather than appearing
   all at once.
6. **Refresh on `/chat/<id>`** — the page loads instead of 404ing. Proves
   `vercel.json` is doing its job.

## The free-tier catch worth knowing

**Render free services sleep after 15 minutes of no traffic.** The next request
wakes it, taking **roughly 50 seconds**. Open WebSockets are dropped when it
sleeps.

For a portfolio link this matters: a recruiter clicks, sees a spinner for most of
a minute, and may leave. Your options, honestly:

- **Accept it** and put a line in your README: *"hosted on a free tier — the
  first load can take up to a minute while the server wakes."* Sets expectations
  and shows you understand the tradeoff.
- **Upgrade** to Render's paid instance. No sleeping.
- **Ping it** every 10 minutes from an uptime checker. Keeps it warm, though it
  burns your monthly free instance hours faster.

Record a GIF of the app working locally and put it at the top of the README
either way. It is the thing people actually look at.

## Redeploying

Both hosts watch your GitHub repo, so:

```bash
git add .
git commit -m "fix: whatever changed"
git push
```

Vercel and Render each rebuild the folder they own. A change under `client/`
does not restart the API, and a change under `server/` does not rebuild the
frontend.

**One catch:** changing a `VITE_*` variable on Vercel does *not* take effect
until you redeploy, because Vite bakes those into the bundle at build time.
**Deployments → ⋯ → Redeploy** after editing one.

## If something is broken

| Symptom | Cause |
| --- | --- |
| `blocked by CORS policy` | `CLIENT_URL` on Render does not exactly match your Vercel origin. Check for a trailing slash. |
| `"db": "disconnected"` on `/api/health` | Atlas Network Access is not `0.0.0.0/0`. |
| Build fails, `package.json not found` | Root Directory is not set to `client` / `server`. |
| 404 refreshing `/chat/<id>` | `client/vercel.json` missing, or Root Directory is wrong so Vercel never read it. |
| Login works, sidebar says `Reconnecting…` | `VITE_SOCKET_URL` is wrong — it should have **no** `/api` suffix. |
| Assistant says "not configured" | `GEMINI_API_KEY` not set on Render, or set with quotes around it. |
| First load takes ~50s | Free tier cold start. Expected. See above. |
